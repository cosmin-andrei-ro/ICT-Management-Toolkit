# ADR 0018 — CMDB: configuration items, relationships and impact

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

IT needs one record of what it runs and how things depend on each other, to see what an incident takes down, what a change may break, and to build later modules (asset management, application portfolio, business impact analysis) on it. The CMDB is the first module after Ticketing; the two must stay separable (CLAUDE.md §5.1).

## Decision

- **Module `Cmdb`** with its own tables (`cmdb_*`), screens, permissions, manual and tests.
- **Item types** (`cmdb_ci_types`) are data, per organization. Their attributes are a Core `FormSchema` (ADR 0011) and the values live in `cmdb_configuration_items.properties` (`jsonb`), keyed by attribute key; history comes from the audit trail.
  - The column is not named `attributes`, which would clash with Eloquent's internal property.
  - Eight default types are created on first use (owner's decision), editable afterwards and never recreated once removed.
  - Type keys are fixed after creation, because imports use them.
- **Items** have an optional identifier, unique per organization regardless of case (partial unique index on `lower(identifier)`; the form checks the same way). Status, environment and criticality are enums with CHECKs. Full-text search covers the name, the identifier, the description and the string attribute values (generated `tsvector`, GIN index).
- **Relationships** (`cmdb_relationships`) are typed "source *type* target": depends on, runs on, uses, is part of, connects to. Composite foreign keys keep both ends in the relationship's organization, and a CHECK forbids self-relationships. Each type states which side a failure affects: for depends on, runs on and uses, the source; for "is part of", the whole. Network links (connects to) propagate nothing, or every switch would affect everything.
- **Impact analysis** runs in PostgreSQL as a recursive CTE with the `CYCLE` clause, at most 10 steps deep, skipping retired and deleted items, sorted by distance and then criticality.
- **Editing (owner's decision):** agents and team leads edit items and relationships (`cmdb.ci.manage`); team leads also manage types (`cmdb.type.manage`); CAB members read (`cmdb.ci.view`).
- **Dependency map:** Cytoscape.js (MIT, no dependencies; owner's decision), registered as an Alpine component (CSP, ADR 0006). It is loaded as a separate chunk only on item pages, and lists of affected and needed items give the same information without the drawing.
- **Links to tickets without coupling the modules:** Core defines two contracts.
  - `ConfigurationItems` lets Ticketing search, link and unlink items and ask for impact. The CMDB implements it; without the CMDB a no-op implementation is used.
  - `LinkedRecords` lets the CMDB show the tickets of an item without knowing tickets. Ticketing registers how to present them, filtered by what the viewer may see.
  - The links live in `cmdb_ci_links`: a foreign key on the item side, polymorphic on the record side, as CLAUDE.md §5.2 allows for cross-cutting links. Linking and unlinking are audited on the ticket.
- **Import (owner's decision, part of this stage):**
  - CSV (comma or semicolon) or XLSX through OpenSpout. The file type is checked by content; at most 2,000 rows and 5 MB.
  - Items are matched by identifier, and empty cells keep current values. Relationships are matched by the identifiers of both items.
  - The preview saves nothing. Importing reads and checks the file again, then saves every row in one transaction, or nothing if any row is invalid.

## Alternatives considered

- **One table per item type, or EAV:** rigid or slow; types must be data that administrators change.
- **A graph database:** another service to run and back up, for graphs that PostgreSQL walks fast at this size.
- **Ticketing pointing to `cmdb_configuration_items` directly:** simpler, but the modules could no longer be enabled separately.
- **Importing the valid rows and skipping the others:** convenient, but partial imports of a CMDB are hard to notice and to repair.

## Consequences

- Asset management (ITAM) and DCIM will reference items rather than duplicate them.
- Change conflicts can later be computed per item (two changes on the same item at the same time) instead of by window only.
- Automatic discovery (agents, network scans, cloud APIs) can feed the same import logic.
